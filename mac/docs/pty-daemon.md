# アプリを閉じても claude を動かし続ける（PTY の常駐プロセス）— 設計と実現性

Issue #174 の検討結果。アプリ（claude-deck）を終了・入れ替え・クラッシュしても、ホストしていた `claude` を止めずに動かし続け、
アプリを開き直したらつなぎ直せるようにする仕組みの設計と、最小の試作での実現性の確認をまとめる。

- 状態: **設計と試作のみ**（アプリのコードは変えていない）。
- 結論（詳細は末尾の「判断」）: **進める**。ただし #173（自動再開）を先に仕上げ、その上に「既定は無効」の設定として段階的に載せる。
  見送り条件（下の「リスクと見送り条件」）のどれかに当たったら、その段階で止めて #173 の `--resume` だけで運用する。

---

## 1. 今の構造（なぜアプリと一緒に終わるか）

- `HostedSession` が `ClaudeTerminalView`（SwiftTerm の `LocalProcessTerminalView` の派生）を 1 つ持ち、
  `launchClaude` で `/bin/zsh -lic "unset ANTHROPIC_API_KEY ANTHROPIC_AUTH_TOKEN; exec claude [--resume=<uuid>]"` を forkpty で起動する
  （`mac/Sources/ClaudeDeck/Terminal/ClaudeTerminalView+Launch.swift`）。環境は `buildSafeEnvironment` で API キーと子セッション印を除く。
- PTY の master はアプリのプロセスが持つ。アプリが終わると master が閉じ、claude（PTY の制御端末を持つセッションリーダー）は **SIGHUP** で終わる。
- 端末ビューは画面に載せず、受信バイトを SwiftTerm に流して **実画面を読む**のに使う（選択待ちの判定・権限 / 選択肢カード・上限表示の検出。
  `+Screen` / `+Input` / `+Limit`）。会話そのものは transcript（`~/.claude/projects/...jsonl`）から組むので、端末のスクロールバックには依らない。
- 上限到達の強制終了は 2 経路: 公式の残量（`LimitWatch` が `MonitorStore.usage` を見る）と、画面末尾の上限表示（`+Limit.scan`）。
  どちらも `reachLimit()` → `terminate()`、残れば 1.5 秒後に **自分の子なら** SIGKILL（`isLiveChild` は `ppid == getpid()` で確かめる）。
- アプリの SIGTERM / SIGINT は何もしないハンドラで捕まえて通常の終了経路に乗せる（`SIG_IGN` は exec を越えて残るため使わない）。

つまり「アプリを閉じても動かし続ける」には、**PTY の master をアプリの外のプロセスが持つ**しかない（#173 の `--resume` は会話を戻すだけで、作業は一度止まる）。

## 2. 案の比較

| 案 | 中身 | 長所 | 短所 | 評価 |
|----|------|------|------|------|
| **A. セッションごとの常駐（アプリから setsid で切り離す）** | 新しい SPM 実行ファイル `claude-deck-pty` を `.app` に同梱。ルームを開く時にアプリが `posix_spawn`（`POSIX_SPAWN_SETSID`）で 1 セッション 1 プロセス起動。常駐側が forkpty で claude を持ち、Unix ドメインソケットで待つ。claude が終われば常駐側も終わる | dtach と同じ単純な形。1 つ壊れても他に波及しない。登録・承認（Login Items）が要らず ad-hoc 署名・`swift run` でも動く。寿命が claude と一致するので掃除が単純 | セッション数だけプロセスが増える（1 つ数 MB）。発見は置き場所の走査 | **推奨** |
| B. LaunchAgent の常駐 1 つ（`SMAppService.agent`） | launchd が 1 つの常駐を管理し、全セッションの PTY を持つ | launchd が起動・再起動してくれる | 署名済みバンドルと Login Items での承認が要る（ad-hoc・`swift run` で不安定）。全セッションが 1 プロセスに乗るので落ちたら全滅し、再起動しても PTY は戻らない（KeepAlive の利点が無い）。多重化のプロトコルが要る | 不採用 |
| C. XPC サービス（バンドル内） | アプリの XPC サービスに PTY を持たせる | 接続と権限は OS 任せ | **XPC サービスの寿命はアプリに紐づく**（アプリが終われば止まる）。目的を満たさない | 不採用 |
| D. tmux / dtach / screen | 外部ツールに PTY を任せる | 実績がある | ツールの導入が要る（Issue で「やらない」）。API キー除去・上限の強制終了を外のツール越しに保証しにくい | 不採用 |
| E.（補助）アプリを常駐化 | 最後のウィンドウを閉じても終わらず、メニューバーに残る | 数十行で済み、iPhone 連携・通知・フックもそのまま生きる | ⌘Q・アプリの入れ替え・クラッシュでは止まる | A の前段として**別に入れる価値あり**（下の段階 0） |

A を推す理由: 目的（アプリが居なくても PTY が生きる）に対して最小で、今の「1 ルーム = 1 PTY」の形をそのまま保てる。
launchd に任せても PTY の子は常駐側と一緒に死ぬので、B の「管理してもらえる」利点はこの用途ではほぼ無い。

## 3. 構成（推奨案 A）

```
 ┌─────────────────────── claude-deck.app（アプリ） ───────────────────────┐
 │ ChatModel / HostedSession                                                │
 │   └ ClaudeTerminalView（SwiftTerm の TerminalView。画面には載せない）      │
 │        ├ 受信: 常駐側から来たバイトを feed（実画面の鏡）                    │
 │        │      → 選択待ち判定・カード・上限表示の検出は今のまま              │
 │        └ 送信: send(txt:) を PTYTransport へ                               │
 │   PTYTransport（protocol）                                                │
 │        ├ LocalTransport  … 今の forkpty（設定が無効の時・試験用）          │
 │        └ DaemonTransport … Unix ソケットで常駐側に接続                      │
 │   PTYDaemonDirectory … 起動時に置き場所を走査してつなぎ直す・古いものを掃除 │
 └───────────────▲─────────────────────────────────────────────────────────┘
                 │ Unix ドメインソケット（0600・同じ uid・トークン）
                 │ アプリが終わっても切れるのは接続だけ
 ┌───────────────┴──── claude-deck-pty（セッションごと・setsid 済み・ppid=1） ┐
 │ PTY master ── forkpty ──▶ /bin/zsh -lic "unset …; exec claude [--resume]"  │
 │ headless の SwiftTerm Terminal（同じ大きさ）… 画面の写し・問い合わせへの応答 │
 │ LimitGuard（MonitorKit）… 画面末尾の上限表示 + usage.json で強制終了          │
 │ 出力は接続が無くても常に読み続ける（claude が書き込みで詰まらない）          │
 └──────────────────────────────────────────────────────────────────────────────┘
```

### 置き場所

- ディレクトリ `~/Library/Application Support/claude-deck/pty/`（0700。既定の場所の時だけ作る。`CLAUDE_DECK_PTY_DIR` で差し替え）。
- 1 セッションにつき:
  - `<id>.sock`（0600。bind の前に `umask 0177`、後に `chmod 0600` で二重に）
  - `<id>.json`（0600・原子的に書く）: 常駐の pid と起動時刻（`procStart`）、claude の pid、cwd、プロジェクト id、`--resume` の sessionId、
    常駐の版（ビルド番号）とプロトコルの版、接続用のトークン（32 バイトの乱数の 16 進）。
  - `<id>.exit.json`（claude が終わった時に接続が無ければ残す: 終了状態・時刻・理由（上限 / 通常））。
  - `<id>.log`（常駐側の stderr。0600・小さく保つ）。
- `<id>` は 12 桁の 16 進。**`sun_path` は 104 バイト未満**の制限があるため UUID は使わない（既定の場所なら 80 バイト弱に収まる）。
  ユーザー名が長くて超える時は `confstr(_CS_DARWIN_USER_TEMP_DIR)` 配下に置く（どちらも本人専用・再起動で常駐は消えるので一時領域でも困らない）。

### 起動（アプリ → 常駐）

1. アプリが `buildSafeEnvironment` で環境を作る（今と同じ）。
2. `posix_spawn` で `Contents/MacOS/claude-deck-pty` を起動。属性は
   `POSIX_SPAWN_SETSID | POSIX_SPAWN_SETSIGDEF（全シグナル既定に）| POSIX_SPAWN_SETSIGMASK（空）| POSIX_SPAWN_CLOEXEC_DEFAULT`、
   stdin/stdout は `/dev/null`、stderr は `<id>.log`。引数は `--id <id> --cwd <path> --cols 160 --rows <n> [--resume <uuid>]` だけ。
3. 常駐側は**自分でも**環境から API キーと子セッション印を除き（二重防御）、`--resume` を UUID の形の時だけ受け、
   起動するコマンドは**固定**（`/bin/zsh -lic "unset ANTHROPIC_API_KEY ANTHROPIC_AUTH_TOKEN; exec claude [--resume=<uuid>]"`）。
   任意のコマンドを渡す口は作らない（headless の `-p` 等を差し込めない）。
4. ソケットと `<id>.json` が出来たらアプリが接続する（出来なければ 3 秒で諦めて常駐を止め、従来の起動にも落とさず「起動できない」を出す）。

アプリの終了（⌘Q・SIGTERM・クラッシュ・Xcode の停止）で死ぬのは接続だけ。常駐は別セッション・別プロセスグループなので、
アプリのプロセスグループへのシグナルも届かない（試作で `sid` と `ppid=1` を確認）。

## 4. プロトコル

フレーム = `type: u8` + `length: u32（ビッグエンディアン）` + `payload`。1 フレーム 8MB まで（超えたら切断）。同時に繋げるのは 1 本（新しい接続が来たら前のを外す）。

| 向き | type | 中身 |
|------|------|------|
| アプリ → | `hello` | プロトコルの版・トークン・アプリの版 |
| アプリ → | `input` | PTY に書くバイト（本人のキー入力・貼り付け。今の `send(txt:)` そのもの） |
| アプリ → | `resize` | cols・rows（u16 ×2）→ 常駐が `TIOCSWINSZ`（カーネルが前面のプロセスグループに SIGWINCH）し、headless の端末も同じ大きさに |
| アプリ → | `terminate` | 理由（`close` = ルームを閉じた / `limit` = 上限到達）。常駐が claude に SIGTERM、1.5 秒後に残っていれば SIGKILL |
| アプリ → | `detach` | 接続だけ外す |
| → アプリ | `welcome` | 常駐の版・claude の pid・今の大きさ・今の状態（動作中 / 上限で止めた） |
| → アプリ | `snapshot` | 今の画面の写し（下記）。`welcome` の直後に 1 回 |
| → アプリ | `output` | PTY からの出力（そのまま） |
| → アプリ | `exited` | `waitpid` の状態と理由。送ったら常駐は片付けて終わる |
| → アプリ | `refused` | 版違い・トークン違い・uid 違い |

- **送るシグナルを常駐側で絞る**: `terminate` で claude（自分の子・`waitpid` できるので pid の再利用で他人を殺さない）にだけ出す。任意のシグナル番号は受けない。
- **版の付け方**: プロトコルの版は整数で、アプリは「今の版と 1 つ前」を話せるようにする。プロトコルは小さく保ち、変えない前提で作る（下の「入れ替え」）。

### つなぎ直した時の画面（写し）

試作で 2 つの方法を比べた:

- **生の出力の末尾を貯めて流し直す（ring）**: 全部持っていれば再現できるが、claude の TUI はカーソルの相対移動で書き換えるので、
  **途中で切った末尾だけを流すと画面が崩れる**（試作で不一致を確認）。全部持つのは長時間のセッションでは現実的でない。
- **常駐側に headless の SwiftTerm `Terminal` を持ち、今の画面をエスケープ列に起こして送る（推奨）**:
  RIS → （代替画面なら `?1049h`）→ 各行を絶対位置で、セルごとの文字と SGR（太字・反転・前景 / 背景の 256 色・トゥルーカラー）→ カーソル位置
  → アプリが読むモード（bracketed paste `?2004h`・カーソルキー `?1h`）。試作で **全セル（文字・背景色・反転）とカーソル・モードが一致**した。
  大きさは見えている行だけなので数 KB（試作は生の出力 3.5KB に対し写し 1.5KB）。

スクロールバックは送らない（会話は transcript から組むので要らない）。アプリの端末は、写しを流した後は `output` をそのまま流し続ける鏡になる。
写しに載らない状態（タイトル・マウスモード・カーソルの形・カーソルの表示 / 非表示（SwiftTerm は非公開））はアプリの判定に使っていないので落としてよい。
足りなければ写しに足す。

### 端末への問い合わせ（DSR・DA・OSC 10/11 等）

claude の TUI が端末に問い合わせると、端末エミュレータが答えを PTY に書き戻す。接続が無い間も答える必要があるので **答えるのは常駐側の headless 端末だけ**にする
（試作で headless でも DSR・DA に答えることを確認）。アプリ側の鏡の端末は、パーサーが出す応答（`TerminalView.send(source: Terminal, data:)`、`open`）を
上書きして捨て、本人の入力（`send(txt:)` → `send(data:)`）だけを `input` で送る。二重に答えると claude が入力として受けてしまうため。
背景色の問い合わせ（OSC 11）への答えは今は NSView の色から出ているので、常駐側の `getColors` で同じ値を返す（実機の claude で要確認）。

## 5. 論点ごとの扱い

### サイズ変更
端末ビューは画面に載せないので、今も起動前に約 160 桁に決めたら変えない（README「選択肢カード」）。常駐でも同じで、起動時に `--cols/--rows` で決め、
`resize` は将来の画面表示のための口として残すだけ。つなぎ直した時はアプリが常駐の大きさ（`welcome`）に自分の端末を合わせてから写しを流す。

### 入力の受け渡し
`input` フレームでそのまま PTY に書く。貼り付け → 0.3 秒 → Enter、画像の取り込み待ち、矢印で ❯ を動かして確かめてから Enter 等の手順は
すべてアプリ側（`+Input`）のまま。**判定は鏡の端末の実画面**で行う。接続中は出力が数 ms 遅れて届くだけなので、今の待ち時間（0.3 秒・メニューの 1 歩ごとの待ち）に収まる。

### 選択待ちの判定（実画面の読み取り）
鏡の端末は写し + 以後の出力で常駐の画面と同じになるので、`screenLines` / `highlightReader` / `InputBlock.detect` / `ChoiceMenu` / `PermissionPrompt` は**変更なし**で成り立つ
（背景色・反転も写しで再現されることを試作で確認）。つなぎ直した直後に権限待ちやメニューが出ていれば、写しを流した時点でカードが出る。
アプリが居ない間に出た権限待ちは、claude がそのまま待つだけ（フックは :8766 が無いので取りこぼすが、開き直せば画面から読める）。

### claude の終了検知
常駐側が `waitpid(WNOHANG)` と master の EOF / EIO の両方で見る。接続があれば `exited` を送り、無ければ `<id>.exit.json` を残してから、
ソケットと `<id>.json` を消して終わる。アプリは次の起動時の走査で `exit.json` を読み、ルームを「終了」として出して（#173 の記録と突き合わせ）から消す。
試作で `exit 7` → 状態 7、SIGTERM → シグナル 15 を受け取れ、ソケットも消えることを確認。

### 上限到達時の強制終了（LimitGuard）
**アプリが居ない間も止められないといけない**（課金枠への切り替え表示「You're now using usage credits」を見たら止める、が料金事故ゼロの一部）。
そこで常駐側も MonitorKit に依存して（`claude-deck-channel` と同じ）次を持つ:

1. 画面末尾の上限表示: headless 端末の実画面を出力のたびに 0.3 秒まとめで `LimitGuard.screenLimitLine` に掛ける（今の `+Limit.scan` と同じ）。
2. 公式の残量: `usage.json` を 3 秒ごとに読み、`UsageLimitLatch` で判定（今の `LimitWatch` と同じ。到達はリセット時刻まで覚える）。

どちらかで到達したら常駐側が claude に SIGTERM → 1.5 秒後に SIGKILL（自分の子なので `waitpid` で確かめられ、`isLiveChild` の ppid 判定は要らなくなる）。
アプリが接続中に先に気づいた場合は `terminate(limit)` を送るだけで、殺すのは常に常駐側。結果は `exited`（理由 `limit`）でアプリに戻り、今の警告ダイアログを出す。
上限到達中の新しい起動を止める判断（`LimitWatch.isLimitReached`）はアプリ側のまま。常駐側も起動時に `usage.json` を見て、到達中なら claude を起動せずに終わる。

### API キー除去・子セッション印の除去
アプリ側の `buildSafeEnvironment`（今のまま）+ 常駐側でもう一度除く + シェルで `unset` してから `exec claude` の三重。
常駐側の起動コマンドは固定で、プロトコルにコマンドや環境を渡す口は無い。headless の起動口は作らない。

### シグナルの受け継ぎ
アプリは SIGTERM / SIGINT に何もしないハンドラを入れているが、ハンドラは exec で既定に戻る。無視（`SIG_IGN`）は残るので、
アプリからの起動は `POSIX_SPAWN_SETSIGDEF` で全シグナルを既定に戻し、常駐側は SIGHUP / SIGPIPE を無視したうえで、**fork した子で exec の前に既定に戻す**
（試作でそうしている）。今の「シグナル設定の漏れ」のテスト（`ClaudeDeckTests` の forkpty 経路）を常駐の経路にも足す。

### 掃除（常駐が残り続けた時）
- claude が終われば常駐も終わる（寿命が一致）。ルームを閉じたら `terminate(close)`。
- アプリの起動時に置き場所を走査: `<id>.json` の pid が生きていて、実行ファイルが `claude-deck-pty`・`procStart` が一致し、接続できるものだけつなぎ直す。
  接続できない（`ECONNREFUSED`）ソケットや pid が死んでいるものは消す（試作で常駐を SIGKILL した後のソケットが `ECONNREFUSED` になり、claude も SIGHUP で終わることを確認）。
- 長く放置されたもの: 「アプリが繋いでいない時間が 24 時間を超え、かつ claude が 1 時間出力していない（待機）」なら常駐側が claude に SIGTERM して終わる。
  時間は設定で変えられるようにし、作業中（出力が流れている）のものは止めない。止めたものは #173 の記録から `--resume` できる。
- ログアウト・再起動では全部消える（launchd がユーザーのプロセスを止める）。その後は #173 の自動再開に任せる。

### アプリの入れ替え（常駐側の版が古い）
- `bundle.sh` は `.app` を消して作り直すので、動いている常駐の実行ファイルは消えたファイルとしてそのまま動き続ける（その場で上書きはしない。署名済みファイルを書き換えると読み込み時に殺されうるため、この形を保つ）。
- 新しいアプリは `hello` で版を確かめる。話せる版ならそのまま使う。話せない古い常駐は、ルームに「古い版の常駐で動いています」を出し、
  「終了して再開する」（`<id>.json` の pid を実行ファイル名と `procStart` で確かめてから SIGTERM → claude は SIGHUP で終わる → #173 の `--resume`）を選ばせる。
  作業中に勝手に止めない。
- これを避けるため、プロトコルは最初から小さく固め、変える時は足すだけ（知らないフレームは無視）にする。

### iPhone 連携・iCloud 通知・フック
- Remote API（:8767）・iCloud 通知・フックの受け口（:8766）は**アプリの中のまま**。常駐側はネットワークを一切持たない（LAN に新しい口を作らない）。
- したがってアプリが居ない間は iPhone からは見えず、通知も出ず、フックは取りこぼす。開き直してつなぎ直せば、画面から状態を読み直して元に戻る。
- アプリが居ない間も iPhone から見たいなら、段階 0（アプリの常駐化）で「閉じる = ウィンドウを閉じるだけ」にするのが安い。

### 監視（MonitorStore）との対応
- `registerHostedProcess(pid:)` は claude の pid で今と同じ（pid は `welcome` で受け取る）。つなぎ直した時にもう一度登録する。
- claude の親は常駐になるので「アプリに引き継ぐ」（外部セッションの判定）とは区別がつく（アプリが登録した pid はホスト中として扱う、は今のまま）。
- チャネル（`claude-deck-channel`）は claude の子で `getppid()` を使うだけなので影響なし。

### セキュリティ
- 他ユーザー: ディレクトリ 0700・ソケット 0600 に加え、受け付け時に `getpeereid` で uid を確かめる（試作で実装）。
- 同じユーザーの他プロセス: 同じ uid のプロセスは元々ほぼ何でもできる（端末へのキー入力等）ので完全には防げないが、
  誤って繋がる・ソケットを見つけて叩くのを防ぐため、`<id>.json`（0600）のトークンを `hello` で照合する。
- 口の小ささ: 常駐ができるのは「決まった claude を 1 つ動かす・バイトを中継する・自分の子を止める」だけ。コマンドの実行・ファイルの読み書き・任意のシグナルは無い。
- フレーム長の上限・同時接続 1 本・不正なフレームは切断。

### #173（自動再開）との役割分担

| 場面 | 常駐あり（本 Issue） | 常駐なし・常駐が消えた（#173） |
|------|----------------------|-------------------------------|
| アプリの ⌘Q・入れ替え・クラッシュ | 動き続ける。開き直したらつなぎ直す（会話も作業も途切れない） | `--resume` で起動し直し、作業中だったものに続きを頼む |
| ログアウト・再起動・常駐が落ちた | （消える） | `--resume` |
| 古い版の常駐 | ユーザーが選んだら止めて → | `--resume` |

- #173 の `hosted-sessions.json` に `ptyId`（常駐の `<id>`）を足す。起動時はまず常駐へのつなぎ直しを試し、できなかったものだけ #173 の再開に回す。
  つなぎ直したものには「続きを進めてください」を送らない（止まっていないため）。
- 終了時の確認（#173）は、常駐が有効なら「作業中 N 件はバックグラウンドで続きます」を既定にし、［バックグラウンドで続けて終了］［すべて止めて終了］［キャンセル］にする。
- 設定は「アプリを閉じても claude を動かし続ける」（**既定は無効**）。無効なら今と同じ forkpty（`LocalTransport`）。

## 8. 試作の結果（scratchpad。リポジトリには入れていない）

`claude` は起動せず、`/bin/bash --norc --noprofile -i` と `/bin/cat` で確かめた。試作のプロセス・ソケットは確認後にすべて止めて消した。

**常駐の試作（`ptyd`、約 300 行・Darwin の forkpty / poll / Unix ソケットのみ）**

| 確認 | 結果 |
|------|------|
| 起動側が `posix_spawn(POSIX_SPAWN_SETSID…)` で切り離してすぐ終わる | 常駐は `sid=pgid=自分`・`ppid=1`・制御端末なし。bash は `ttys005` を制御端末に持つ |
| API キー・`CLAUDECODE`・`CLAUDE_CODE_*` を付けて起動 | 子の環境に残らない（`env | grep -cE "ANTHROPIC|CLAUDE"` = 0） |
| 別プロセスから接続して入出力 | `echo hello-$((1+2))` → `hello-3` |
| サイズ変更（`TIOCSWINSZ`） | `stty size` が `24 80` → `40 120`。bash が SIGWINCH で行を描き直した |
| 接続していない間の出力 | 切断後 1 秒で出た `late-output` を、次の接続の再生で受け取れた |
| 接続中のクライアントを SIGKILL | 常駐は残り、次の接続で続きの入出力ができた |
| 終了検知 | `exit 7` → 状態 7、常駐への `SIGTERM` 依頼 → シグナル 15。ソケットは消え、常駐も終わった |
| 常駐を SIGKILL | claude 役（bash）は SIGHUP で終わり、ソケットは残って接続は `ECONNREFUSED`（= 掃除の対象と判定できる） |
| 権限 | ディレクトリ `drwx------`・ソケット `srw-------`。受け付けで `getpeereid` の uid を確かめる |

**画面の写しの試作（`snapcheck`、リポジトリの SwiftTerm のチェックアウトを path 依存で使用。Metal Toolchain が無いので `--build-system native`）**

- 200 行の出力（スクロールバックあり）+ 相対移動での書き換え + 背景色付きのタブ行 + 反転の `❯ 1.` + 日本語 + トゥルーカラーの罫線 + `?2004h` / `?1h` を流した端末 A を写しに起こし、
  新しい端末 B に流すと、**全行の文字・背景色・反転・カーソル位置・bracketed paste・カーソルキーのモードが一致**（写し 1,466 バイト / 元の出力 3,488 バイト）。
- 同じ出力の末尾 300 バイトだけを流した端末は**一致しない**（生の出力を切って再生する方式は不可）。
- headless の端末も DSR（`ESC[6n`）・DA（`ESC[c`）に答える（`ESC[1;1R`・`ESC[?65;…c`）。

**付録: 要点のコード（試作から）**

```swift
// 切り離して起動（アプリ側）
posix_spawnattr_setflags(&attr, Int16(POSIX_SPAWN_SETSID | POSIX_SPAWN_SETSIGDEF | POSIX_SPAWN_SETSIGMASK | POSIX_SPAWN_CLOEXEC_DEFAULT))
var all = sigset_t(); sigfillset(&all); posix_spawnattr_setsigdefault(&attr, &all)

// 常駐側: fork 前に argv/envp を C 文字列で用意し、子では割り当てずに exec
let pid = forkpty(&master, nil, nil, &ws)
if pid == 0 { signal(SIGHUP, SIG_DFL); signal(SIGPIPE, SIG_DFL); execve(argv[0]!, argv, envp); _exit(127) }

// 受け付け: 同じ uid だけ
var uid: uid_t = 0, gid: gid_t = 0
if getpeereid(fd, &uid, &gid) != 0 || uid != getuid() { close(fd) }

// 写し: RIS → 各行を絶対位置で、セルごとに SGR（style・fg・bg）と文字（全角の後半 width==0 は飛ばす）→ カーソル → モード
out += "\u{1b}c"; /* 行ごと */ out += "\u{1b}[\(row + 1);1H" + sgr(cell.attribute) + String(cell.getCharacter())
out += "\u{1b}[\(cur.y + 1);\(cur.x + 1)H" + (t.bracketedPasteMode ? "\u{1b}[?2004h" : "") + (t.applicationCursor ? "\u{1b}[?1h" : "")
```

試作で**確かめていないこと**: 本物の claude（Ink 系の TUI）を載せた時の問い合わせと再描画、上限表示の検出、`.app` からの起動（試作は CLI から）、TCC の帰属。

## 9. 判断: 進める

**進める**（ただし順番と条件付き）。

理由:
- 試作で、切り離し・ソケットでのつなぎ直し・接続の無い間の出力の保持・サイズ変更・終了検知・異常時の掃除の判定・uid の確認がすべて素直に動いた。
  外部ツール無しで、Darwin の API と既に依存している SwiftTerm だけで作れる。
- いちばん心配だった「つなぎ直した後の実画面の読み取り（選択待ちの判定・タブの背景色）」は、常駐側の headless 端末の写しで**セル単位まで一致**し、
  アプリ側の判定コードを変えずに済む見込みが立った。
- 料金事故ゼロの方針（API キー除去・headless 不可・上限の強制終了）は、常駐側にも同じ判定（MonitorKit の LimitGuard）を持たせ、起動コマンドを固定することで、
  アプリが居ない間も保てる設計にできる。
- #173 と競合せず、「常駐で途切れさせない」→「消えたら `--resume`」の二段構えになる。

条件:
1. #173（自動再開）を先に完了させる（常駐が消えた時の受け皿になるため）。
2. 段階 0（アプリの常駐化）は安く効果が大きいので、先に別 Issue として入れてよい。
3. 段階 1 の終わりで本物の claude を載せて確かめ、上の「見送り条件」（問い合わせの答えで崩れる・写しで判定を誤る・常駐側で上限を止められない）に当たれば、
   そこで見送り、#173 の `--resume` だけで運用する。
4. 設定は既定で無効のまま入れ、段階 4 の実機確認を経てから既定を変えるか決める。
